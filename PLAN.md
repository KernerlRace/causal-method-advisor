# Causal Method Advisor — план реализации

**Задача (от преподавателя, формат хакатона):** дан CSV и вопрос на естественном языке («Повлияла ли акция на продажи?», «Что вызывает отток?»).
**Своя, написанная с нуля модель** объясняет, какую методологию причинного анализа лучше применить.
Если вопрос сложный или данных не хватает, она даёт варианты лучшего решения.

**Ограничения:**
- Готовые LLM нельзя: ни Claude, ни Qwen/Llama, ни HuggingFace-веса.
- Архитектура, токенизатор и обучение — наши.
- Дедлайна нет.

**Железо:** RTX 3060 Ti (8 GB), Ryzen 5 3600, 16 GB RAM.
Этого хватает, чтобы обучить трансформер на 20–40M параметров за часы.

**Источники знаний для карточек методов (пишем своими словами):**
- Molak, *Causal Inference and Discovery in Python*: гл. 6–14 и эпилог;
- Facure, *Causal Inference for the Brave and True*: гл. 25 (SDID) и главы про DiD и SC.

---

## 1. Реалистичная постановка: какую «свою LLM» мы можем сделать

Модель с нуля на 20–40M параметров **не станет ChatGPT**: свободного диалога на любые темы не будет.
Зато в **узкой задаче** она может работать хорошо:
- понять вопрос про причинность;
- найти в CSV колонки воздействия (treatment) и результата (outcome);
- выбрать метод;
- написать объяснение.

Условие: обучить её на большом и разнообразном **синтетическом датасете**, который мы сами генерируем.

Ключевая идея: CSV генерируются из сценариев с **известным механизмом порождения данных (DGP)**.
Поэтому правильный метод для каждого примера известен по построению.
Например, «панель, 1 treated-юнит, тренды не параллельны → SDID/SC, не DiD».
Модель учится на истине, а не на мнениях другой LLM.

### Архитектура: модель + детерминированные инструменты

| Компонент | Что делает | Своё / готовое |
|---|---|---|
| **Профайлер CSV** (Python) | структура данных: панель или cross-section, типы колонок, n, кандидаты в unit/time/treatment/outcome | свой код |
| **Диагностики** (Python) | pre-trend тест, overlap, баланс, размер donor pool, нормальность остатков | свой код + statsmodels/sklearn |
| **Rule engine** | жёсткие ограничения: SDID без колонки времени невозможен и т.п.; страхует от галлюцинаций | свой код |
| **CausalGPT-mini** (наша модель) | понимает вопрос, выбирает колонки, ранжирует методы, оценивает уверенность, пишет объяснение | **с нуля** |

Это та же логика, что в книге Молака (гл. 11, с. 287–288).
Языковые модели ошибаются в причинных рассуждениях непредсказуемо, поэтому статистику считает код, а модель понимает и объясняет.
Для маленькой модели это ещё важнее.

## 2. Пайплайн инференса (два прохода модели)

```
CSV + вопрос
   │
   ▼
[1] Профайлер ─────────► data_card (сериализуется в текст для модели)
   │
   ▼
[2] Модель, проход 1 ──► тип вопроса, treatment, outcome, unit, time
   │                      (constrained decoding: колонки только из этого CSV)
   ▼
[3] Диагностики ───────► pre-trends p-value, overlap, n_treated, n_pre_periods, ...
   │
   ▼
[4] Модель, проход 2 ──► распределение вероятностей по методам + объяснение
   │                      (вход: data_card + вопрос + результаты диагностик)
   ▼
[5] Rule engine ───────► отсеивает невозможные методы, перенормирует вероятности
   │
   ▼
[6] Режим ответа:
     p(top1) высокая и отрыв от top2 большой → «Рекомендация: X, потому что…»
     иначе                                   → «Вопрос сложный, варианты: A / B / C,
                                                 выбирайте A, если…» + чего не хватает
     причинный вывод невозможен             → честный отказ + что собрать
```

Требование «если вопрос сложный — дать варианты» решается естественно: через **калиброванную уверенность** модели, а не через захардкоженное правило.

## 3. Сама модель: CausalGPT-mini

### 3.1 Токенизатор (с нуля)
- Byte-level BPE, свой код обучения слияний, словарь около 8–16k, EN + RU.
- Спецтокены:
  - разметка: `<CARD>`, `<COL>`, `<Q>`, `<DIAG>`, `<ANS>`, `<EXPL>`, `<EOS>`;
  - метод = **один** токен: `<M:did>`, `<M:sdid>`, `<M:psm>`, …;
  - тип вопроса: `<T:effect>`, `<T:discovery>`, `<T:counterfactual>`, `<T:not_causal>`, `<T:unidentifiable>`.
- **Сделано (этап 5):** типы — те, что реально есть в данных (`effect`, `heterogeneity`, `discovery`, `not_causal`),
  плюс `<MODE:recommend|options|refuse>`, `<PARSE>` и `<PAD>`; `<M:*>` строятся из карточек.
  Текст пользователя кодируется с `allow_special=False`, чтобы «<M:did>» в вопросе не стал служебным токеном.
- ~~Словарь обучен только на SFT-шаблонах, на незнакомом тексте ≈2 символа на токен.~~
  **Сделано (этап 7):** переобучен на корпусе + SFT, словарь 16 384; Википедия EN/RU — 4.2 / 3.6 символа на токен,
  примеры задачи — 4.9 / 5.2, целый пример по-прежнему влезает в 1024 (максимум 829).

### 3.2 Архитектура (с нуля на PyTorch-примитивах)
- Decoder-only трансформер в стиле GPT.
- Сами пишем causal self-attention, MLP, LayerNorm/RMSNorm, RoPE, weight tying.
- Из PyTorch берём только `nn.Linear`, `nn.Embedding` и autograd. HuggingFace не используем.
- Стартовый размер: 8 слоёв, d_model 512, 8 голов, контекст 1024. Это около 30M параметров.
- Обучение: AdamW, cosine LR, mixed precision (fp16) на 3060 Ti, gradient accumulation.
- **Сделано (этап 6):** `model/transformer.py` — pre-norm блоки с RMSNorm, RoPE, SwiGLU (скрытый слой 1408),
  без bias, weight tying, KV-кэш для генерации; 29.9M параметров.
  - Внимание написано вручную; для обучения есть быстрый путь `attention="sdpa"` (flash-ядро PyTorch),
    тесты сверяют его с ручным до 1e-5. На батче 8×1024: 58k против 26k токенов/с, 3.2 против 6.1 GB.
    Ручное нужно для визуализации внимания (бонус-этап).
  - Вместо fp16 — **bf16**: 3060 Ti (Ampere) его умеет, а GradScaler не нужен. fp16 остался запасным путём.
  - Данные: тексты → поток uint16 на диске (`model/data.py`) → случайные окна; SFT целиком — 35M токенов.

### 3.3 Обучение в два этапа

**Этап A — претрейн (язык и предметная лексика):**
- Корпус из открытых текстов: статьи Википедии RU/EN по статистике, эконометрике и ML (CC BY-SA), наши карточки методов, наши тексты-объяснения.
- Книгу Facure можно взять, если подтвердится открытая лицензия (проверить LICENSE в репозитории).
- Книгу Молака в обучение **не кладём**: это защищённый текст, и маленькая модель может начать воспроизводить его дословно. Используем её только как источник знаний для наших карточек.
- Объём: десятки миллионов токенов, это часы обучения на 3060 Ti.

**Сделано (этап 7):** `datagen/corpus.py`.
- Википедия: обход категорий (статистика, эконометрика, причинность, ML — глубже; маркетинг, здоровье, HR, образование,
  ритейл — на один уровень, ради лексики вопросов). EN 8787 статей / 74M символов, RU 2211 / 13M.
  Точные дубли (перенаправления в категориях) убираются до деления train/val по документам.
- Facure — только текстовые ячейки (MIT); наши карточки и объяснения из train-части SFT (20k) — 12% токенов.
- Википедия ограничивает частоту: запросы с Retry-After и повторами, по 2 потока на язык, выгрузка докачивается.
- Решения по замерам: словарь 16k (8k/12k хуже сжимают статьи), lr 1e-3 (лучше 6e-4 и 1.5e-3 на коротком прогоне),
  батч 8×4 (16×2 со словарём 16k переполнял 8 GB, и Windows уводил память в общую — скорость падала с 45k до 20k ток/с).
- Плато задаёт объём корпуса: train-val разрыв ~0.1 к концу. Если претрейн не поможет на живых вопросах — сначала
  расширять корпус, а не модель.

**Этап B — SFT на задаче.** Пример обучающей последовательности:

```
<CARD> rows=1209 structure=panel unit=state time=year
<COL> state:cat(39) year:int(1970-2000) cigsale:float treated:bool after_treatment:bool
<Q> Снизил ли закон Prop 99 продажи сигарет в Калифорнии?
<ANS> <T:effect> treatment=treated outcome=cigsale unit=state time=year
<DIAG> n_treated=1 n_controls=38 pre_periods=19 pretrend_p=0.003
<ANS> <M:sdid> 0.71 <M:sc> 0.22 <M:did> 0.02 ...
<EXPL> Один treated-штат и 38 контрольных, 19 лет до закона. Тренды до закона
не параллельны (p=0.003), поэтому обычный DiD будет смещён... <EOS>
```

- Loss считаем **только на ответной части** (`<ANS>`, `<EXPL>`).
- Распределение по методам учим через soft-labels: несколько допустимых методов с весами из gold-разметки сценария. Так у модели появляется калиброванная уверенность.

### 3.4 Constrained decoding
- В проходе 1 после `treatment=` разрешены только токены имён колонок из этого CSV. Модель физически не может выдумать колонку.
- Методы берутся только из словаря `<M:*>`.
- Вероятности по методам читаются из softmax в позиции метода, а не из сгенерированного текста.

## 4. Генератор обучающих данных (самая важная часть)

Качество маленькой модели определяется разнообразием данных, а не размером.

### 4.1 Сценарии (DGP) → CSV + gold
Для каждого метода пишем генератор, который рандомизирует параметры: n, число юнитов и периодов, силу конфаундинга, шум, наличие инструмента, нелинейность, лишние колонки-шум, пропуски.

| Сценарий | Gold (допустимые методы) |
|---|---|
| RCT, бинарный treatment | diff-in-means; для CATE — meta-learners/uplift |
| Наблюдательные данные, конфаундеры наблюдаемы, n мало | регрессия, PSM, IPW |
| То же, n большое, нелинейность | DR, DML; для CATE — CausalForestDML |
| Непрерывный treatment | LinearDML, CausalForestDML |
| Ненаблюдаемый конфаундер + инструмент | IV |
| Ненаблюдаемый конфаундер + полный медиатор | front-door |
| Назначение по порогу | RDD |
| Панель, много treated, параллельные тренды | DiD (SDID тоже ок) |
| Панель, 1–3 treated, тренды не параллельны | SDID, SC |
| Панель, staggered adoption | SDID по когортам, Callaway–Sant'Anna |
| Один временной ряд, нет контролей | ITS, CausalImpact |
| «Что на что влияет», графа нет | PC / GES / LiNGAM; FCI при скрытых конфаундерах |
| Ненаблюдаемый конфаундер, нет ни IV, ни медиатора | **отказ** + sensitivity analysis |
| Вопрос про прогноз, а не причинность | `<T:not_causal>`: это задача ML, не causal inference |

### 4.2 Вопросы
- Грамматика перефразов EN/RU: сотни шаблонов × синонимы. **Основной язык — английский** (преподаватель англоязычный), русский — дополнительный.
  - «повлияло ли», «какой эффект», «увеличивает ли», «что будет, если», «из-за чего»…
- Колонкам даём **разные имена**: `sales` / `revenue` / `выручка` / `y` / `target` / `col_7`. Модель учится связывать смысл вопроса с колонкой по названию и по профилю, а не запоминать имена.
- Шум: опечатки, разговорный стиль, лишние детали.

### 4.3 Объяснения
- Шаблоны с вариативностью (несколько формулировок на каждый факт).
- В шаблон подставляются реальные цифры из диагностик. Модель учится опираться на факты.
- Отдельные шаблоны «почему не X» для отвергнутых альтернатив.

**Объём:** 100–300k примеров SFT, генерируются автоматически.

> Можно ли размножать перефразы вопросов через внешнюю LLM? Это ускорило бы работу, но может нарушить требование «с нуля». **По умолчанию не используем**. Если преподаватель разрешит, это даст прирост на живых вопросах.

## 5. База знаний: карточки методов

Каждый метод описан YAML-карточкой. Карточку читают rule engine (ограничения), генератор объяснений (факты) и UI (справка рядом с ответом).

```yaml
id: sdid
name: Synthetic Difference-in-Differences
question_types: [effect]
estimand: ATT
requires: {structure: panel, treated_units: ">=1", control_units: ">=5", pre_periods: ">=5"}
assumptions: [no anticipation, SUTVA, параллельность после взвешивания юнитов и периодов]
diagnostics: [pretrend_test, unit_weights_dispersion, placebo_variance]
prefer_over:
  did: тренды до воздействия не параллельны
  sc: нужна меньшая дисперсия; уровень может не совпадать (intercept)
avoid_when: [экстраполяция через intercept опасна → классический SC]
staggered: разбить на блоки по когортам, ATT взвесить по числу treated-наблюдений
source: Facure гл. 25
```

Набор методов:
- **RCT:** diff-in-means, CUPED, S/T/X/DR-learners (uplift).
- **Back-door:** регрессия, matching, PSM, IPW, DR/TMLE, LinearDML, CausalForestDML.
- **Другие стратегии идентификации:** IV, front-door, RDD.
- **Панели и ряды:** DiD/TWFE, SC, SDID, ITS/CausalImpact.
- **Discovery:** PC, GES, LiNGAM, NOTEARS, FCI.
- **Если эффект не идентифицируем:** sensitivity analysis.

## 6. Rule engine (жёсткие ограничения, не ранжирование)

```
нет колонки времени            → запрещены DiD, SC, SDID, ITS
нет контрольных юнитов в панели → запрещены DiD, SC, SDID; разрешён ITS
treatment непрерывный           → запрещены PSM, diff-in-means; разрешены DML и регрессия
нет переменной-порога           → запрещён RDD
pre_periods < 3                 → SC/SDID помечаются «ненадёжно»
вопрос <T:discovery>            → только методы discovery
```

Модель ранжирует, правила маскируют. Если после маскировки вероятность размазана, включается режим «варианты».

## 7. Формат ответа

```json
{
  "question_type": "effect",
  "mapped": {"treatment": "treated", "outcome": "cigsale", "unit": "state", "time": "year"},
  "mode": "recommendation",
  "methods": [
    {"id": "sdid", "p": 0.71}, {"id": "sc", "p": 0.22}, {"id": "did", "p": 0.02}
  ],
  "diagnostics": {"pretrend_p": 0.003, "n_treated": 1, "n_controls": 38, "pre_periods": 19},
  "explanation": "Один treated-штат, 38 контрольных, тренды до закона не параллельны → ...",
  "rejected": {"did": "параллельные тренды не выполняются"},
  "assumptions_to_check": ["no anticipation", "нет перетока на соседние штаты"],
  "missing_info": []
}
```

## 8. Оценка качества

1. **Тест на синтетике** (отложенные сценарии и шаблоны, не виденные при обучении):
   - точность типа вопроса;
   - точность treatment и outcome;
   - top-1 и top-3 точность выбора метода.
2. **Живые вопросы — главная метрика.** 150–300 вопросов, написанных людьми (вы, одногруппники) к реальным CSV. Шаблонный тест завышает качество, живой показывает правду.
3. **Реальные датасеты:**
   - `smoking.csv` (Prop 99): ожидаем SDID/SC. Эталоны: DiD −27.3, SC −19.5, SDID −15.6;
   - Hillstrom: uplift.
4. **Ловушки:** неидентифицируемый вопрос, нет контролей, вопрос про прогноз, нарушенный overlap. Метрика — доля корректных отказов и режимов «варианты».
5. **Калибровка:** когда модель уверена на 80%, права ли она примерно в 80% случаев? Это обосновывает режим «варианты».
6. **Сравнение с бейзлайнами (сильный слайд для защиты):**
   - только rule engine;
   - классический ML: TF-IDF + логрегрессия для вопроса, градиентный бустинг для метода;
   - наш трансформер без претрейна;
   - наш трансформер с претрейном.

**Вывод после этапа 6.** Шаблонный test почти насыщен уже через 12 минут обучения, поэтому решения на этапах 7–8 принимаем по **живым вопросам** (`eval/human_questions.jsonl`) — их пора собирать. Свободная генерация придумывает колонки (`instrument`, которой нет в карточке), так что constrained decoding на этапе 8 обязателен. Проверочный прогон — ещё не этап 8: loss по всей последовательности, а не только по ответу.

Этап 4 намеренно стоит **до** нейросети. Демо работает рано, а модель потом заменяет бейзлайн и показывает измеримый прирост.

## 12. Риски

| Риск | Что делаем |
|---|---|
| Модель хорошо работает на шаблонах и плохо на живых вопросах | больше разнообразия в грамматике; живой тест-сет с первых этапов; претрейн для общего языка |
| Модель выдумывает колонки и методы | constrained decoding + rule engine |
| Объяснение противоречит цифрам | цифры подставляются из диагностик, проверка согласованности перед выводом |
| Мало данных для претрейна | модель меньше (10–15M); упор на SFT; это задача узкого домена |
| Библиотеки не ставятся на Python 3.14 | venv на 3.12 |
