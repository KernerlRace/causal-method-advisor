# Causal Method Advisor — план реализации

**Задача (от преподавателя, формат хакатона):** дан CSV и вопрос на естественном языке («Повлияла ли акция на продажи?», «Что вызывает отток?»).
**Своя, написанная с нуля модель** объясняет, какую методологию причинного анализа лучше применить.
Если вопрос сложный или данных не хватает, она даёт варианты лучшего решения.

**Ограничения:**
- Готовые LLM нельзя: ни Claude, ни Qwen/Llama, ни HuggingFace-веса.
- Архитектура, токенизатор и обучение — наши.
- Дедлайна нет.

**Железо:** RTX 3060 Ti (8 GB), Ryzen 5 3600, 16 GB RAM.
Этого хватает, чтобы обучить трансформер на 20–40M параметров за часы.

**Источники знаний для карточек методов (пишем своими словами):**
- Molak, *Causal Inference and Discovery in Python*: гл. 6–14 и эпилог;
- Facure, *Causal Inference for the Brave and True*: гл. 25 (SDID) и главы про DiD и SC.

## 1. Реалистичная постановка: какую «свою LLM» мы можем сделать

Модель с нуля на 20–40M параметров **не станет ChatGPT**: свободного диалога на любые темы не будет.
Зато в **узкой задаче** она может работать хорошо:
- понять вопрос про причинность;
- найти в CSV колонки воздействия (treatment) и результата (outcome);
- выбрать метод;
- написать объяснение.

Условие: обучить её на большом и разнообразном **синтетическом датасете**, который мы сами генерируем.

Ключевая идея: CSV генерируются из сценариев с **известным механизмом порождения данных (DGP)**.
Поэтому правильный метод для каждого примера известен по построению.
Например, «панель, 1 treated-юнит, тренды не параллельны → SDID/SC, не DiD».
Модель учится на истине, а не на мнениях другой LLM.

### Архитектура: модель + детерминированные инструменты

| Компонент | Что делает | Своё / готовое |
|---|---|---|
| **Профайлер CSV** (Python) | структура данных: панель или cross-section, типы колонок, n, кандидаты в unit/time/treatment/outcome | свой код |
| **Диагностики** (Python) | pre-trend тест, overlap, баланс, размер donor pool, нормальность остатков | свой код + statsmodels/sklearn |
| **Rule engine** | жёсткие ограничения: SDID без колонки времени невозможен и т.п.; страхует от галлюцинаций | свой код |
| **CausalGPT-mini** (наша модель) | понимает вопрос, выбирает колонки, ранжирует методы, оценивает уверенность, пишет объяснение | **с нуля** |

Это та же логика, что в книге Молака (гл. 11, с. 287–288).
Языковые модели ошибаются в причинных рассуждениях непредсказуемо, поэтому статистику считает код, а модель понимает и объясняет.
Для маленькой модели это ещё важнее.

## 2. Пайплайн инференса (два прохода модели)

```
CSV + вопрос
   │
   ▼
[1] Профайлер ─────────► data_card (сериализуется в текст для модели)
   │
   ▼
[2] Модель, проход 1 ──► тип вопроса, treatment, outcome, unit, time
   │                      (constrained decoding: колонки только из этого CSV)
   ▼
[3] Диагностики ───────► pre-trends p-value, overlap, n_treated, n_pre_periods, ...
   │
   ▼
[4] Модель, проход 2 ──► распределение вероятностей по методам + объяснение
   │                      (вход: data_card + вопрос + результаты диагностик)
   ▼
[5] Rule engine ───────► отсеивает невозможные методы, перенормирует вероятности
   │
   ▼
[6] Режим ответа:
     p(top1) высокая и отрыв от top2 большой → «Рекомендация: X, потому что…»
     иначе                                   → «Вопрос сложный, варианты: A / B / C,
                                                 выбирайте A, если…» + чего не хватает
     причинный вывод невозможен             → честный отказ + что собрать
```

Требование «если вопрос сложный — дать варианты» решается естественно: через **калиброванную уверенность** модели, а не через захардкоженное правило.

**Сделано (этап 9):** `advisor/confidence.py`, `eval/calibrate.py`.
- Мягкая метка учит softmax по методам «насколько метод подходит», а не «насколько вероятно, что лучший назван верно»:
  у «sdid 1.0, sc 0.4, did 0.1» цель — 0.67 на sdid, хотя top-1 верен в 99.1% случаев. Температура T = 0.087,
  подобранная на val (цель — равномерное распределение по лучшим методам эталона: два равно лучших — по 0.5),
  превращает это в вероятность правоты: ECE на test 0.310 → 0.015. Токен режима калиброван и так (ECE 0.001).
  У модели этапа 9.3 (переобучена, калибровка собрана заново): T = 0.086, ECE на test 0.326 → 0.018.
- Уверенность — калиброванная масса лучшего *разрешённого* метода без перенормировки после маски правил: если модель
  ставила на запрещённый метод, она неверно поняла данные, и остаток не должен выглядеть уверенным.
- Отказ — не по порогу: вопрос не причинный, правила запретили всё, лучший метод — анализ чувствительности.
- Схема «p(top1) высокая и отрыв большой → рекомендация» в чистом виде проиграла токену модели (сбалансированная
  точность режима на val 96.9% против 99.9%): «варианты» в эталоне — это два метода с весом ≥ 0.9, то есть близость
  весов (did 1.0 / sdid 0.8 — рекомендация, sdid 1.0 / sc 0.9 — варианты), а не неуверенность в лучшем — он верен в
  обоих случаях. Выбрано правило «осторожнее из двух» (токен или уверенность ниже 0.23 / отрыв меньше 0.02; у модели
  этапа 9.3 — 0.25 / 0.01): на val оно равно токену, а вне обучающего распределения превращает неуверенные ответы
  в варианты. Протокол выбора
  (пороги и правило — только по val, при равенстве — осторожнее) записан до запуска на ловушках и ручных вопросах.
- Калибровка лежит в `models/calibration.json` с отпечатком файла модели; для другой модели она не применяется
  (тогда T = 1 и режим — токен, как на этапе 8).

**Сделано (этап 9, часть 2): уверенность в разборе.** Проход 2 верит разбору: при неверном воздействии он уверенно
отвечает на другой вопрос. Теперь проход 1 записывает вероятность каждого выбора (`Advisor.last_parse`): тип среди
четырёх `<T:*>`, ключ каждого поля, значение — по токенам среди тех, что продолжают хоть одну колонку этого CSV (это
распределение по колонкам, тест сверяет его с перебором дерева префиксов). Произведение по типу и ролям — собственная
вероятность модели, что тип и роли разобраны верно.
- Калибровать на val оказалось не на чем: модель разбирает верно все 4988 вопросов val — в val только знакомые
  шаблоны, отложенные есть лишь в test. По правилу, записанному до подсчёта (протокол в заметках сессии), если неверных
  разборов на val меньше 30, уверенность — сама вероятность модели без подбора, порог «попросить подтвердить роли» —
  её 1%-квантиль на val, 0.9998 (на знакомых вопросах просим 1 раз из 100); у модели этапа 9.3 — 0.99904.
- Режим ответа уверенность в разборе не меняет: «варианты» — это «подходят несколько методов», а не «я мог неверно
  понять вопрос». Ниже порога интерфейс называет самую неуверенную часть разбора («не уверен, что воздействие —
  `age15to24`»), подсвечивает это поле и помечает совет как предварительный; роли, подтверждённые пользователем,
  не проверяются.

## 3. Сама модель: CausalGPT-mini

### 3.1 Токенизатор (с нуля)
- Byte-level BPE, свой код обучения слияний, словарь около 8–16k, EN + RU.
- Спецтокены:
  - разметка: `<CARD>`, `<COL>`, `<Q>`, `<DIAG>`, `<ANS>`, `<EXPL>`, `<EOS>`;
  - метод = **один** токен: `<M:did>`, `<M:sdid>`, `<M:psm>`, …;
  - тип вопроса: `<T:effect>`, `<T:discovery>`, `<T:counterfactual>`, `<T:not_causal>`, `<T:unidentifiable>`.
- **Сделано (этап 5):** типы — те, что реально есть в данных (`effect`, `heterogeneity`, `discovery`, `not_causal`),
  плюс `<MODE:recommend|options|refuse>`, `<PARSE>` и `<PAD>`; `<M:*>` строятся из карточек.
  Текст пользователя кодируется с `allow_special=False`, чтобы «<M:did>» в вопросе не стал служебным токеном.
- ~~Словарь обучен только на SFT-шаблонах, на незнакомом тексте ≈2 символа на токен.~~
  **Сделано (этап 7):** переобучен на корпусе + SFT, словарь 16 384; Википедия EN/RU — 4.2 / 3.6 символа на токен,
  примеры задачи — 4.9 / 5.2, целый пример по-прежнему влезает в 1024 (максимум 829).

### 3.2 Архитектура (с нуля на PyTorch-примитивах)
- Decoder-only трансформер в стиле GPT.
- Сами пишем causal self-attention, MLP, LayerNorm/RMSNorm, RoPE, weight tying.
- Из PyTorch берём только `nn.Linear`, `nn.Embedding` и autograd. HuggingFace не используем.
- Стартовый размер: 8 слоёв, d_model 512, 8 голов, контекст 1024. Это около 30M параметров.
- Обучение: AdamW, cosine LR, mixed precision (fp16) на 3060 Ti, gradient accumulation.
- **Сделано (этап 6):** `model/transformer.py` — pre-norm блоки с RMSNorm, RoPE, SwiGLU (скрытый слой 1408),
  без bias, weight tying, KV-кэш для генерации; 29.9M параметров.
  - Внимание написано вручную; для обучения есть быстрый путь `attention="sdpa"` (flash-ядро PyTorch),
    тесты сверяют его с ручным до 1e-5. На батче 8×1024: 58k против 26k токенов/с, 3.2 против 6.1 GB.
    Ручное нужно для визуализации внимания (бонус-этап).
  - Вместо fp16 — **bf16**: 3060 Ti (Ampere) его умеет, а GradScaler не нужен. fp16 остался запасным путём.
  - Данные: тексты → поток uint16 на диске (`model/data.py`) → случайные окна; SFT целиком — 35M токенов.

### 3.3 Обучение в два этапа

**Этап A — претрейн (язык и предметная лексика):**
- Корпус из открытых текстов: статьи Википедии RU/EN по статистике, эконометрике и ML (CC BY-SA), наши карточки методов, наши тексты-объяснения.
- Книгу Facure можно взять, если подтвердится открытая лицензия (проверить LICENSE в репозитории).
- Книгу Молака в обучение **не кладём**: это защищённый текст, и маленькая модель может начать воспроизводить его дословно. Используем её только как источник знаний для наших карточек.
- Объём: десятки миллионов токенов, это часы обучения на 3060 Ti.

**Сделано (этап 7):** `datagen/corpus.py`.
- Википедия: обход категорий (статистика, эконометрика, причинность, ML — глубже; маркетинг, здоровье, HR, образование,
  ритейл — на один уровень, ради лексики вопросов). EN 8787 статей / 74M символов, RU 2211 / 13M.
  Точные дубли (перенаправления в категориях) убираются до деления train/val по документам.
- Facure — только текстовые ячейки (MIT); наши карточки и объяснения из train-части SFT (20k) — 12% токенов.
- Википедия ограничивает частоту: запросы с Retry-After и повторами, по 2 потока на язык, выгрузка докачивается.
- Решения по замерам: словарь 16k (8k/12k хуже сжимают статьи), lr 1e-3 (лучше 6e-4 и 1.5e-3 на коротком прогоне),
  батч 8×4 (16×2 со словарём 16k переполнял 8 GB, и Windows уводил память в общую — скорость падала с 45k до 20k ток/с).
- Плато задаёт объём корпуса: train-val разрыв ~0.1 к концу. Если претрейн не поможет на живых вопросах — сначала
  расширять корпус, а не модель.

**Этап B — SFT на задаче.** Пример обучающей последовательности:

```
<CARD> rows=1209 structure=panel unit=state time=year
<COL> state:cat(39) year:int(1970-2000) cigsale:float treated:bool after_treatment:bool
<Q> Снизил ли закон Prop 99 продажи сигарет в Калифорнии?
<ANS> <T:effect> treatment=treated outcome=cigsale unit=state time=year
<DIAG> n_treated=1 n_controls=38 pre_periods=19 pretrend_p=0.003
<ANS> <M:sdid> 0.71 <M:sc> 0.22 <M:did> 0.02 ...
<EXPL> Один treated-штат и 38 контрольных, 19 лет до закона. Тренды до закона
не параллельны (p=0.003), поэтому обычный DiD будет смещён... <EOS>
```

- Loss считаем **только на ответной части** (`<ANS>`, `<EXPL>`).
- Распределение по методам учим через soft-labels: несколько допустимых методов с весами из gold-разметки сценария. Так у модели появляется калиброванная уверенность.

**Сделано (этап 8):** `model/sft.py`, `model/train_sft.py`.
- Формат: `<CARD>…<Q>…<PARSE>разбор<DIAG>диагностики<ANS><MODE:m> <M:a> 1.00 …<EXPL>объяснение<EOS>`.
  Последовательность собирается по сегментам тем же кодом, что и на инференсе; текст пользователя — без спецтокенов.
- Loss — на разборе вместе с закрывающим `<DIAG>` и на ответе до `<EOS>` (37% токенов). Позиция первого метода —
  мягкая метка (веса эталона, нормированные в распределение). Её loss к концу 0.827 при энтропии самих меток 0.821:
  модель воспроизводит распределение почти точно.
- Логиты считаются только в позициях с целью (`GPT.hidden`): по всей длине словарь 16k занимал 6.6 GB и уводил память
  в общую, теперь 2.4 GB. Батч 8×4, примеры похожей длины в одном батче.
- Потолок нагрузки (`model/limits.py`): пауза после каждого микробатча — GPU в среднем ~60%, пики до 75%; CPU ~22%.
  Эпоха на 90k примерах — 22 мин (без потолка было бы ~13).

### 3.4 Constrained decoding
- В проходе 1 после `treatment=` разрешены только токены имён колонок из этого CSV. Модель физически не может выдумать колонку.
- Методы берутся только из словаря `<M:*>`.
- Вероятности по методам читаются из softmax в позиции метода, а не из сгенерированного текста.

**Сделано (этап 8):** `model/decode.py`.
- Проход 1: тип — argmax по `<T:*>`; дальше поля по одному. Ключ (treatment, outcome, …, конец разбора) — по вероятности
  его слова; значение — по токенам: argmax только среди токенов, продолжающих хотя бы один разрешённый вариант (колонки
  этого CSV; для порога — только числовые; yes/no). Грамматика: для effect обязательны treatment и outcome, поля — в
  каноническом порядке, колонка — один раз. Разбор по полям токенизируется так же, как целиком (проверено на 3000 примерах val).
- Пробовали выбирать значение по вероятности всей последовательности токенов (ветки от общего KV-кэша): на ручных вопросах
  хуже жадного (роли 78 и 72 из 93 против 80 и 78 у моделей с претрейном и с нуля) — сумма log-вероятностей тянет к коротким
  именам. Среднее на токен — 80 и 72. Оставили жадный выбор; на демо-вопросе про Prop 99 модель с претрейном из-за него
  называет воздействием `age15to24` — известная ошибка.
- Проход 2: режим — argmax по `<MODE:*>`, методы — softmax по `<M:*>` в мягкой позиции, запрещённые правилами убираются.
- Объяснение модель пишет сама; показывается, только если каждое число и каждая доля («172%» ↔ `rel=1.72`) есть во входе и
  назван лучший метод. Иначе — шаблонное объяснение, и интерфейс об этом говорит. На эталонных объяснениях проверка
  не даёт ни одного ложного срабатывания (4988 примеров val).

## 4. Генератор обучающих данных (самая важная часть)

Качество маленькой модели определяется разнообразием данных, а не размером.

### 4.1 Сценарии (DGP) → CSV + gold
Для каждого метода пишем генератор, который рандомизирует параметры: n, число юнитов и периодов, силу конфаундинга, шум, наличие инструмента, нелинейность, лишние колонки-шум, пропуски.

| Сценарий | Gold (допустимые методы) |
|---|---|
| RCT, бинарный treatment | diff-in-means; для CATE — meta-learners/uplift |
| Наблюдательные данные, конфаундеры наблюдаемы, n мало | регрессия, PSM, IPW |
| То же, n большое, нелинейность | DR, DML; для CATE — CausalForestDML |
| То же, но воздействие почти предрешено ковариатами (плохой overlap, `backdoor_targeted`, этап 9) | **варианты:** DR после обрезки по propensity score, PSM с калипером; регрессия ниже (экстраполирует), IPW последним |
| Непрерывный treatment | LinearDML, CausalForestDML |
| Ненаблюдаемый конфаундер + инструмент | IV |
| Ненаблюдаемый конфаундер + полный медиатор | front-door |
| Назначение по порогу | RDD |
| Панель, много treated, параллельные тренды | DiD (SDID тоже ок) |
| Панель, 1–3 treated, тренды не параллельны | SDID, SC |
| Панель, staggered adoption | SDID по когортам, Callaway–Sant'Anna |
| Один временной ряд, нет контролей | ITS, CausalImpact |
| «Что на что влияет», графа нет | PC / GES / LiNGAM; FCI при скрытых конфаундерах |
| Ненаблюдаемый конфаундер, нет ни IV, ни медиатора | **отказ** + sensitivity analysis |
| Вопрос про прогноз, а не причинность | `<T:not_causal>`: это задача ML, не causal inference |

### 4.2 Вопросы
- Грамматика перефразов EN/RU: сотни шаблонов × синонимы. **Основной язык — английский** (преподаватель англоязычный), русский — дополнительный.
  - «повлияло ли», «какой эффект», «увеличивает ли», «что будет, если», «из-за чего»…
- Колонкам даём **разные имена**: `sales` / `revenue` / `выручка` / `y` / `target` / `col_7`. Модель учится связывать смысл вопроса с колонкой по названию и по профилю, а не запоминать имена.
- Шум: опечатки, разговорный стиль, лишние детали.

### 4.3 Объяснения
- Шаблоны с вариативностью (несколько формулировок на каждый факт).
- В шаблон подставляются реальные цифры из диагностик. Модель учится опираться на факты.
- Отдельные шаблоны «почему не X» для отвергнутых альтернатив.

**Объём:** 100–300k примеров SFT, генерируются автоматически.

> Можно ли размножать перефразы вопросов через внешнюю LLM? Это ускорило бы работу, но может нарушить требование «с нуля». **По умолчанию не используем**. Если преподаватель разрешит, это даст прирост на живых вопросах.

## 5. База знаний: карточки методов

Каждый метод описан YAML-карточкой. Карточку читают rule engine (ограничения), генератор объяснений (факты) и UI (справка рядом с ответом).

```yaml
id: sdid
name: Synthetic Difference-in-Differences
question_types: [effect]
estimand: ATT
requires: {structure: panel, treated_units: ">=1", control_units: ">=5", pre_periods: ">=5"}
assumptions: [no anticipation, SUTVA, параллельность после взвешивания юнитов и периодов]
diagnostics: [pretrend_test, unit_weights_dispersion, placebo_variance]
prefer_over:
  did: тренды до воздействия не параллельны
  sc: нужна меньшая дисперсия; уровень может не совпадать (intercept)
avoid_when: [экстраполяция через intercept опасна → классический SC]
staggered: разбить на блоки по когортам, ATT взвесить по числу treated-наблюдений
source: Facure гл. 25
```

Набор методов:
- **RCT:** diff-in-means, CUPED, S/T/X/DR-learners (uplift).
- **Back-door:** регрессия, matching, PSM, IPW, DR/TMLE, LinearDML, CausalForestDML.
- **Другие стратегии идентификации:** IV, front-door, RDD.
- **Панели и ряды:** DiD/TWFE, SC, SDID, ITS/CausalImpact.
- **Discovery:** PC, GES, LiNGAM, NOTEARS, FCI.
- **Если эффект не идентифицируем:** sensitivity analysis.

## 6. Rule engine (жёсткие ограничения, не ранжирование)

```
нет колонки времени            → запрещены DiD, SC, SDID, ITS
нет контрольных юнитов в панели → запрещены DiD, SC, SDID; разрешён ITS
treatment непрерывный           → запрещены PSM, diff-in-means; разрешены DML и регрессия
нет переменной-порога           → запрещён RDD
pre_periods < 3                 → SC/SDID помечаются «ненадёжно»
вопрос <T:discovery>            → только методы discovery
```

Модель ранжирует, правила маскируют. Если после маскировки вероятность размазана, включается режим «варианты».

**Исправлено на этапе 9:** панель, где все юниты получили воздействие в один месяц, профайлер не считал дизайном
(колонка меняется только во времени, как «после», а пары-группы нет), и правило «нет контрольных юнитов» не
срабатывало — DiD оставался разрешён. Теперь это дизайн без контролей; карточки обучающих сценариев и демо не
изменились. Заодно проверка нелинейности больше не падает, если разбор назвал исходом категориальную колонку.

## 8. Оценка качества

1. **Тест на синтетике** (отложенные сценарии и шаблоны, не виденные при обучении):
   - точность типа вопроса;
   - точность treatment и outcome;
   - top-1 и top-3 точность выбора метода.
2. **Живые вопросы — главная метрика.** 150–300 вопросов, написанных людьми (вы, одногруппники) к реальным CSV. Шаблонный тест завышает качество, живой показывает правду.
   - **Сделано (этап 8), первая часть:** `eval/handwritten_questions.jsonl` — 93 вопроса (69 EN, 24 RU) к 12 демо-датасетам,
     написанные вручную мимо грамматики шаблонов (синонимы вместо имён колонок, разговорный стиль, опечатки, длинный
     контекст). Эталон — из сценария датасета. Это строже шаблонного test, но писались они во время разработки, а не
     сторонними людьми, — вопросы от других людей всё ещё нужны, и по ним надо проверять следующие правки грамматики.
3. **Реальные датасеты:**
   - `smoking.csv` (Prop 99): ожидаем SDID/SC. Эталоны: DiD −27.3, SC −19.5, SDID −15.6;
   - Hillstrom: uplift.
4. **Ловушки:** неидентифицируемый вопрос, нет контролей, вопрос про прогноз, нарушенный overlap. Метрика — доля корректных отказов и режимов «варианты».
   - **Сделано (этап 9):** `eval/traps.py` — 48 вопросов (36 EN, 12 RU) к шести датасетам `data/traps/` со своими
     механизмами порождения (`scripts/make_traps.py`) и к демо. Ожидаемый ответ записан до первого запуска; ответ
     засчитывается только при верных типе и ролях. Бейзлайн / модель по токену / модель с калибровкой: скрытый
     конфаундер 25 / 17 / 17%, нет контролей 92 / 25 / 92%, прогноз 50 / 67 / 67%, плохой overlap 0 / 0 / 0%,
     всего 42 / 27 / 44%; при эталонном разборе — 75 / 56 / 77%.
   - **Этап 9.3, плохой overlap — повод для вариантов** (эталон `datagen` и переобучение, без нового порога). Плохой
     overlap при верном разборе: бейзлайн 0 → 100%, модель 8 → 100%; сквозь пайплайн бейзлайн 0 → 67%, модель 0 → 8%
     (на этих двух датасетах модель по-прежнему путает роли, и проверка разбора просит подтвердить все 11 ошибок).
     Всего 48 ловушек: бейзлайн 42 → 58%, модель 44 → 40%; при эталонном разборе обе — 100% (было 75 и 77%).
     Модель потеряла три вопроса «нет контролей» на разборе (`emails_sent` вместо воздействия).
5. **Калибровка:** когда модель уверена на 80%, права ли она примерно в 80% случаев? Это обосновывает режим «варианты».
   - **Сделано (этап 9):** на шаблонном test — да (ECE 0.015 после температуры, до неё 0.310). На 93 ручных вопросах
     (только отчёт) — частично: средняя уверенность 0.89 у верных ответов и 0.72 у неверных, ECE 0.175; из 44 ответов
     с уверенностью ≥ 0.9 верны 82%.
   - **Уверенность в разборе (этап 9, часть 2), только отчёт.** Ранжирует хорошо, но вне знакомых формулировок не
     калибрована: AUROC верного разбора против неверного 0.973 на отложенных шаблонах test, 0.879 на ручных вопросах,
     0.936 на ловушках; ECE 0.123 / 0.152 / 0.259 (на знакомых шаблонах test — 0.0001). На отложенных шаблонах модель
     в среднем уверена на 0.95 при 83% верных разборов. Порог 0.9998 ловит 73 из 74, 12 из 13 и 25 из 25 неверных
     разборов (110 из 112), но просит подтвердить и 25% / 22.5% / 52% верных. У модели этапа 9.3 (порог 0.99904):
     AUROC 0.875 / 0.866 / 0.925, ловит 39 из 41, 12 из 14 и 27 из 28 (78 из 83), просит подтвердить 35% / 24% / 60%
     верных; на отложенных шаблонах верных разборов больше — 90.4% против 82.7%.
6. **Сравнение с бейзлайнами (сильный слайд для защиты):**
   - только rule engine;
   - классический ML: TF-IDF + логрегрессия для вопроса, градиентный бустинг для метода;
   - наш трансформер без претрейна;
   - наш трансформер с претрейном.

**Вывод после этапа 6.** Шаблонный test почти насыщен уже через 12 минут обучения, поэтому решения на этапах 7–8 принимаем по **живым вопросам** (`eval/human_questions.jsonl`) — их пора собирать. **Вывод после этапа 8.**
- Модель обгоняет бейзлайн там, где он слаб: связать слова вопроса с колонкой («free delivery» → `free_shipping`,
  «recovery time» → `recoveryDays`). Ограниченное декодирование не даёт ей назвать чужую колонку.
- Слабые места — те же, что у шаблонов: контекст, сказанный не так, как в грамматике («randomly assigned the flag»,
  «hard cutoff on appraisal_score»), модель теряет (на шаблонном test те же поля почти всегда верны); тип вопроса на ручных
  вопросах хуже, чем у бейзлайна (87% против 95%): «dose-response effect» уходит в heterogeneity, «causally related» — в
  not_causal. Тип вопроса на незнакомых шаблонах — 82.7%, хуже проверочного прогона этапа 6 (92.0%): тогда loss был и на
  тексте вопроса, теперь только на ответе. Кандидаты: вспомогательный loss на вопросе и богаче грамматика контекста —
  проверять уже на вопросах от других людей, а не на этих 93: под них грамматику подгонять нельзя.
- Претрейн нужен прежде всего ради текста: без него модель пишет объяснения того же вида, но с чужими числами.
- В приложении нейросеть работает локально (`models/causalgpt.pt`, 65 MB bf16); демо в облаке остаётся на бейзлайне,
  пока не решено, как отдавать PyTorch и веса (этап 10).

**Вывод после этапа 9.**
- Калиброванная уверенность честна на данных, похожих на обучающие, и ловит один вид ошибки вне их: выбор модели
  запрещён правилами. На панелях без контрольной группы токен модели 9 раз из 12 рекомендует, а уверенность после
  маски падает — ответ становится вариантами. На ручных вопросах так же ушли в варианты три вопроса, ошибочно
  прочитанные как heterogeneity.
- Главное узкое место — разбор: на новых датасетах ловушек модель называет воздействием `annual_spend`, исходом —
  `income` или `age` (роли верны в 4 и 0 из 12 вопросов), а проход 2 принимает неверный разбор за чистую монету:
  10 из 13 неверных ответов на ручных вопросах — с уверенностью ≥ 0.7. Следующий шаг — уверенность самого разбора
  (вероятности выбора типа и колонок в проходе 1), чтобы спрашивать «воздействие — это X?».
- Плохой overlap не ловит ни одно правило даже при верном разборе: в обучающем эталоне плохой overlap никогда не
  повод для вариантов (в RDD он по построению, в backdoor_small эталон всё равно «рекомендация»). Чинить — в эталоне
  `datagen` и переобучением, а не порогом, подогнанным под ловушки.
- Ловушки, как и 93 ручных вопроса, написаны во время разработки; вопросы от других людей по-прежнему нужны.

**Вывод после уверенности в разборе (этап 9, часть 2).**
- Собственная вероятность разбора хорошо отделяет неверные разборы от верных, но вне обучающих формулировок завышена.
  Порог, выбранный на знакомых вопросах, ловит почти все ошибки разбора ценой частых переспросов на незнакомых: это
  честный обмен, пока переспрос дёшев (роли и так показаны в шаге 1).
- Все 75 ошибок разбора на test — неверный тип вопроса; на ручных вопросах и ловушках ошибаются и роли.
- Не видит: уверенную ошибку (вопрос о дозе прочитан как heterogeneity с вероятностью 0.99995) и неверный метод при
  верном разборе (7 из 17 неверных ответов на ручных вопросах).
- Чтобы калибровать и снизить ложные тревоги, нужны неверные разборы на незнакомых формулировках вне test: отложенные
  шаблоны в val или вопросы от других людей. После переобучения модели (плохой overlap) калибровку разбора надо собрать
  заново: `eval.calibrate collect --parse` на val и test и `fit`.

**Вывод после этапа 9.3 (плохой overlap).**
- Ошибка была в эталоне, а не в модели: флаг poor_overlap диагностики ставили и раньше, но в обучающих данных он
  встречался только в RDD (там по построению) и в 6% малых back-door, где эталон всё равно говорил «регрессия». Новый
  эталон опирается на тот же флаг и прежние константы `advisor/diagnostics.py`; диапазоны сценария `backdoor_targeted`
  (наклон логита 1.5–8, 200–20 000 строк) записаны до первого прогона ловушек и после него не менялись.
- Новый сценарий разыгрывается вторым жребием (`datagen/scenarios/__init__.py`, `ADDED`): остальные сиды дают прежние
  сценарии, перестроено 2556 из 50 000, и сравнение «до / после» почти попарное.
- При верном разборе плохой overlap теперь всегда «варианты» у обоих бэкендов. Сквозной результат упирается в разбор:
  бейзлайн берёт 8 из 12 ловушек, модель — 1, потому что на этих датасетах путает роли, как и на этапе 9; проверка
  разбора спрашивает про все 11 ошибок.
- Ручные вопросы, метод сквозь пайплайн, 78.8 → 67.5%: 14 потеряно, 5 приобретено, ни одна потеря не связана с overlap
  (при верном разборе — 80 из 80). Десять — проход 1 читает вопрос иначе, хотя его цель в обучении не менялась;
  четыре — близкий выбор на демо A/B-теста (разность средних и регрессия 0.49 / 0.41 → 0.31 / 0.44), когда разбор не
  видит рандомизации. Контроль — ещё два запуска с другим сидом (только отчёт; в приложении остаётся запуск,
  записанный в протокол): на данных этапа 9 и на новых данных — по 72.5%. При том же сиде смена данных итог не
  меняет, а запуски расходятся на 5–11 пунктов. Плохой overlap при верном разборе (по токену) — 0% на старых данных
  и 100% на новых в обоих сидах: это эффект эталона.
- Две проблемы измерения. 93 ручных вопроса не различают модели, обученные одним рецептом: один запуск сдвигает итог
  на 5–11 пунктов, нужны несколько запусков или больше вопросов (от других людей). Файл сценариев несёт
  подгонки синтетического контроля, сделанные до перехода решателя на cvxpy: пересборка панелей текущим кодом меняет
  флаг SC примерно у пятой части. Панели оставлены как были, чтобы менять одно за раз; полная пересборка — следующий шаг.
- Калибровка собрана заново (файл привязан к модели): T метода 0.086, ECE на test 0.326 → 0.018, правило снова
  «осторожнее из двух»; порог разбора 0.99904, вне знакомых формулировок ловит 78 из 83 неверных разборов (было 110 из 112).

**Вывод после этапа 10.**
- Ранжирование решено у обоих бэкендов: при верном разборе метод верен почти всегда. Вся разница — в чтении вопроса:
  модель лучше связывает слова с колонками (роли на ручных вопросах 84.9% против 64.5%, по-русски 91.7% против 54.2%),
  бейзлайн лучше определяет тип вопроса (94.6% против 89.2%) и на ловушках сквозь пайплайн (58% против 40%).
- Выпущенный запуск сам по себе не значимо лучше бейзлайна по методу сквозь пайплайн (+10.0, [−1.2, +21.2]); рецепт —
  значимо (три запуска из четырёх). Запуск зафиксирован протоколом (сид 0) и на лучший не заменяется: иначе это подгонка
  под 93 вопроса.
- Демо-вопросы нашли ошибку, которую не видит ни одна уверенность: «действует на исход только через skills_score»
  прочитано как инструмент с уверенностью 0.99999. Данные инструмент и медиатор не различают (оба связаны с воздействием
  и исходом, исключающее ограничение и полную медиацию проверить нельзя), поэтому решение — не порог, а явное
  допущение словами в шаге 1 для любого инструмента или медиатора из разбора (`role_assumptions`). Метрики не меняются.
- Следующее — по-прежнему вопросы от других людей и пересборка панелей; для решений между близкими моделями — несколько
  запусков или усреднение их предсказаний.

Этап 4 намеренно стоит **до** нейросети. Демо работает рано, а модель потом заменяет бейзлайн и показывает измеримый прирост.

## 12. Риски

| Риск | Что делаем |
|---|---|
| Модель хорошо работает на шаблонах и плохо на живых вопросах | больше разнообразия в грамматике; живой тест-сет с первых этапов; претрейн для общего языка |
| Модель выдумывает колонки и методы | constrained decoding + rule engine |
| Объяснение противоречит цифрам | цифры подставляются из диагностик, проверка согласованности перед выводом |
| Мало данных для претрейна | модель меньше (10–15M); упор на SFT; это задача узкого домена |
| Библиотеки не ставятся на Python 3.14 | venv на 3.12 |
